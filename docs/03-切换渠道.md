# 3. 两个渠道随时切换

「随时切换」难的不是把请求发到哪，而是**订阅那边有一份 CLI 自己的会话**，它得和后端的库对得上。用户在 API 渠道聊了十句再切回订阅，或者在订阅下改了前面一句话、重新生成、按了停止——这时 CLI 会话里装的和后端组出来的就不一样了。

## 3.1 三档

后端每次要在订阅渠道发一轮，先问一句：**桥上那个会话里装的，和我这一轮组出来的历史（不算用户刚发的这一句），是不是同一份？**

| 档 | 什么时候 | 怎么做 | 缓存 |
|---|---|---|---|
| **接着说** | 是同一份，会话指纹也没变 | 只把这一句推进活着的会话 | 最满，思考块天然都在 |
| **退一步** | 和会话里**更早的某一处**对得上，之后只差这一句 | 从那一处分叉：`resume` + `resumeSessionAt` + `forkSession` | 前缀一样，照读 |
| **重铸** | 都对不上 | 用后端库里这一页的历史铸一份新会话，交给 CLI `resume` | 看改动在哪（3.5） |

各种操作落在哪一档：

- **退一步**：重新生成最新那条、左右翻回原来那个版本、改用户最后一句、删掉最后一来回。
- **重铸**：改 / 删前面的话、按过停止、换了页、换了模型或思考强度、改了系统提示词或工具、从 API 渠道切回来、会话被 CLI 压缩过。

## 3.2 比哈希，不列清单

「对不对得上」**不要**一条条写「编辑过吗、删过吗、换过模型吗」——以后每加一个功能都可能漏一条。改成比哈希：

- 每一轮在订阅下好好跑完，后端记一行**检查点**：「这一页历史到这里为止」的哈希 + 这一轮的**会话指纹** → CLI 的会话号 + 会话里最新一条的 uuid。
- 下一轮组好历史后，算同样的两个哈希去找检查点：
  - 找到了，而且那条 uuid 就是会话最新一条 → 接着说；
  - 找到了，但那条 uuid 不是最新的（后面还有被翻掉、被重新生成掉的）→ 退一步；
  - 找不到 → 重铸。

哪种改动都不用单独写判断。检查点只是缓存的索引，丢了也只是下一句重铸。

**会话指纹**包括所有「变了就必须开新会话」的东西：模型、系统提示词、思考设置和强度、工具清单（连说明和入参格式）、开着哪几件 CLI 自带工具。这和 API 渠道「工具变了整页缓存重写」是同一回事。

```ts
import { createHash } from "node:crypto";

// 一样的东西一定得到一样的哈希：块是从库里原样读出来的，键的先后不变
const hashOf = (value: unknown) => createHash("sha256").update(JSON.stringify(value)).digest("hex");

type SessionPlan =
  | { mode: "append"; sessionId: string; at: string }   // 接着说 / 退一步（桥自己看 at 是不是最新的）
  | { mode: "rebuild"; base: string | null };           // 重铸；base = 上一个会话，桥从它抄开头几块

function planSession(db: Db, conversationId: number, req: ChatRequest): { fingerprint: string; session: SessionPlan } {
  const fingerprint = hashOf({
    model: req.model,
    system: req.system,
    thinking: req.thinking,
    effort: req.effort,
    tools: req.toolSpecs,
    builtinTools: req.builtinTools,
  });
  const history = toAnthropicMessages(req.turns).slice(0, -1);   // 不算用户刚发的这一句
  const found = db.get(
    `SELECT session_id, entry_uuid FROM sdk_checkpoint
      WHERE conversation_id = ? AND fingerprint = ? AND prefix_hash = ?
      ORDER BY id DESC LIMIT 1`,
    conversationId, fingerprint, hashOf(history),
  );
  if (found) return { fingerprint, session: { mode: "append", sessionId: found.session_id, at: found.entry_uuid } };
  const last = db.get(`SELECT session_id FROM sdk_checkpoint WHERE conversation_id = ? ORDER BY id DESC LIMIT 1`, conversationId);
  return { fingerprint, session: { mode: "rebuild", base: last?.session_id ?? null } };
}
```

**检查点按「下一轮会组出来的样子」记**，不是按「刚才交给桥的那份」记。两者有时不一样：比如某一轮工具结果是一张截图，交给模型的是图，库里存的是一段文字描述；下一轮组出来的历史里就是文字。按交给桥的那份记的话，下一轮永远对不上，每句都重铸。做法是这一轮存进库以后，再用组请求的同一个函数组一遍历史，拿它算哈希：

```ts
function recordCheckpoint(db: Db, conversationId: number, plan: Plan, result: BridgeResult) {
  if (!result.reusable || !result.sessionId || !result.lastUuid) return;   // 停过、出过错的不记，下一句重铸
  const next = toAnthropicMessages(composeTurns(db, conversationId, plan.target).turns);
  const history = next.at(-1)?.role === "user" ? next.slice(0, -1) : next; // 末尾挂着的工具结果见 4.5
  db.run(
    `INSERT INTO sdk_checkpoint (conversation_id, fingerprint, prefix_hash, session_id, entry_uuid, created_at)
     VALUES (?, ?, ?, ?, ?, ?)`,
    conversationId, plan.fingerprint, hashOf(history), result.sessionId, result.lastUuid, Date.now(),
  );
  // 每个对话留最近一两百行就够，退一步用得上的都在里面
}
```

调试的时候很想知道「这一句为什么重铸了」。可以顺手把每条消息的短哈希也存一份，对不上时和上一个检查点逐条比，说得出「是指纹里哪一样变了」或者「第几条消息对不上」。

## 3.3 桥这边怎么接

后端只说 `append`（带会话号和那一处的 uuid）或 `rebuild`（带整页历史），具体是接着写、从磁盘 `resume`、还是分叉，由桥看自己的状态决定：

```js
prepare(turn) {
  const { conversation, session } = turn;
  const current = this.live.get(conversation);
  if (current?.busy) throw new BridgeError("busy");

  if (session.mode === "append") {
    // 活着的进程、同一个会话、同一个指纹、最新一条就是后端说的那一处：直接往里写
    if (current && current.sessionId === session.sessionId &&
        current.fingerprint === turn.fingerprint && current.lastUuid === session.at) {
      return current;
    }
    this.close(conversation);
    const path = findTranscript(this.config, session.sessionId);
    if (!path) throw new BridgeError("session_missing");          // 后端会当场改成重铸再发一次
    if (isTail(readEntries(path), session.at)) {
      return this.open(conversation, turn, { resume: session.sessionId });                     // 进程关了，从磁盘接
    }
    return this.open(conversation, turn, { resume: session.sessionId, resumeSessionAt: session.at, forkSession: true }); // 退一步
  }

  // 重铸
  this.close(conversation);
  const sessionId = randomUUID();
  if (session.history.length === 0) return this.open(conversation, turn, { sessionId });
  const prelude = session.base ? preludeOf(readEntries(findTranscript(this.config, session.base) ?? "")) : [];
  writeTranscript(this.config, sessionId, synthesize({ messages: session.history, sessionId, model: turn.model, prelude }));
  return this.open(conversation, turn, { resume: sessionId });
}
```

后端收到 `session_missing`（会话记录被清了、桥换了机器），**只要还没吐出一个字**，就当场改成重铸再发一次，用户感觉不到。

一轮跑完，桥在 `result` 里告诉后端「这个会话还能不能接着用」：按过停止、出过错、被压缩过的都是不能，桥把进程关掉，后端不记检查点，下一句自然重铸。

## 3.4 重铸：把库里的历史铸成会话记录

CLI 的会话记录是 `CLAUDE_CONFIG_DIR/projects/<工作目录>/<会话号>.jsonl`，一行一个条目，条目之间用 `parentUuid` 串成一条链。重铸就是自己写一份这样的文件，再 `resume` 它。（SDK 也有 `sessionStore` 选项可以在内存里交这些条目，道理一样。）

**这个格式是 CLI 内部的，不保证稳定。** 所以 SDK 钉死版本，升级前先跑第 7 章的自测：「铸一份 → 发一句 → 模型记得上一句、缓存读数正常」。

实测几个结论：

- 全部条目换新会话号、重新串 uuid，**照样读满缓存**。缓存只认发出去的字节，不认 uuid。
- **只用后端库里的消息铸，缓存会断在第一句**：CLI 在每个会话第一句前面自己塞了几段（运行环境、模型身份、日期），后端的库里没有这几段，铸出来的第一句就和原来不一样，缓存只剩系统提示词那一截。
- 所以：**有旧会话的话，把旧会话第一句前面 CLI 塞的那几块原样抄过来**，放在第一句后面（和 CLI 自己写的位置一样）。认不出的种类不抄——抄错了比不抄更糟，不抄只是缓存少读一截。

```js
// CLI 在第一句前面塞的那几种（实测看到的）
const PRELUDE_TYPES = new Set(["environment", "model", "date", "session_context"]);

export function preludeOf(entries) {
  const out = [];
  for (const entry of entries) {
    if (entry.type === "assistant") break;
    if (entry.type === "attachment" && PRELUDE_TYPES.has(entry.attachment?.type)) out.push(entry);
  }
  return out;
}

// 后端的历史（Anthropic 格式的 messages，块原样）→ 会话记录条目
export function synthesize({ messages, sessionId, cwd, version, model, prelude = [] }) {
  const entries = [];
  let parent = null;
  const common = () => ({ parentUuid: parent, isSidechain: false, userType: "external", entrypoint: "sdk-ts",
                          cwd, sessionId, version, gitBranch: "", timestamp: new Date().toISOString() });
  const push = (entry) => { entries.push(entry); parent = entry.uuid; };

  messages.forEach((message, index) => {
    if (message.role === "user") {
      push({ ...common(), type: "user", uuid: randomUUID(), promptId: randomUUID(),
             message: { role: "user", content: message.content } });
      if (index === 0) for (const block of prelude) push({ ...block, ...common(), uuid: randomUUID() });
    } else {
      push({ ...common(), type: "assistant", uuid: randomUUID(), requestedModel: model,
             message: { id: `msg_rebuilt_${index}`, type: "message", role: "assistant", model,
                        content: message.content, stop_reason: "end_turn", stop_sequence: null,
                        usage: { input_tokens: 0, output_tokens: 0 } } });
    }
  });
  return entries;
}
```

`version` 写成 CLI 的版本号（和它自己写的一样），`cwd` 写桥的工作目录。思考块、工具调用和结果、图都原样放在 `content` 里。

**从 API 渠道第一次切过来、或者旧会话记录被清掉了**，没有可抄的，只能全用后端的历史从头铸，这一次多写一点缓存。

## 3.5 重铸一定会整页重写缓存吗

不一定。缓存认的是「从开头起逐字节一样的那一段」，CLI 每一轮都在最后一条挂缓存，所以：

- **只动了最后几块**（按停止、改倒数第二句）：铸出来的前面那一大段要是和原来**逐字节一样**，就能接上上一轮写下的缓存，只重写最后那点。
- **动了很前面的话**：系统提示词和工具那段照读，后面的历史整段重写。
- 所以「铸出来的字节和 CLI 活着时发的一样」很要紧，抄开头那几块主要就是为了这个。

## 3.6 切渠道时的思考块

后端存的思考块带着上游签的签名。回放规则（两个渠道都一样）：

- **这条回复是同一个模型写的** → 思考块原样带上。
- **是别的模型写的** → 思考块丢掉，文字留着。

「同一个模型」要按渠道上实际的模型 id 比。同一个模型在不同渠道叫法可能不一样（订阅叫 `claude-opus-5-5`，某些转发商叫 `anthropic/claude-opus-5.5`），这种按「不是同一个」处理最稳妥：丢掉思考块只是少一点上下文，带错了可能直接 400。

```ts
const THINKING = new Set(["thinking", "redacted_thinking"]);

function replayAssistant(blocks: Block[], writtenBy: string, now: string): Block[] {
  return writtenBy === now ? blocks : blocks.filter((block) => !THINKING.has(block.type));
}
```

另外，新一代模型的思考块绑定它前面的前缀，前缀变了回传会作废甚至报错。换窗时带过去的原话一律去掉思考块，就是这个原因（见第 5 章）。

**工具调用也要按渠道排。** 订阅下存下来的工具调用和结果，先后顺序 CLI 认、API 不认，原样回放给 API 会 400。给 API 回放时要把重叠的调用重新配对，见 4.8。

## 3.7 保温（续命）

用户停下来以后，每隔一段时间按「下一句」的样子读一次缓存，让它别过期。1 小时档的缓存，隔 50 分钟左右保一次（实测隔 45–58 分钟都能读满）。

API 渠道：照最后一次请求原样再发一次，最后一句换成一个占位字，收到开头一帧（`message_start` 里已经有缓存读写的数）就挂断。

订阅渠道多一个约束：**不能往活着的会话里写**，那样保温那句会进模型的历史，和后端对不上。做法是**从会话里后端说的那一处分叉一份不存的**：

```js
async keepalive(turn) {
  const input = inputQueue();
  const q = query({
    prompt: input.iterable,
    options: queryOptions(turn, this.config, {        // 选项和真聊时一模一样，不然前缀不一样就是整页重写
      mcpServers: relayServer(turn.tools, async () => ({ content: "Not available.", isError: true })),
      canUseTool: async () => ({ behavior: "deny", message: "no tools in keepalive" }),
      resume: turn.session.sessionId,
      resumeSessionAt: turn.session.at,
      forkSession: true,
      persistSession: false,                          // 分叉出来的不存
      maxTurns: 1,
    }),
  });
  const timer = setTimeout(() => q.interrupt().catch(() => {}), 120_000);
  try {
    input.push([{ type: "text", text: "." }]);
    for await (const message of q) {
      if (message.type === "stream_event" && message.event?.type === "message_start") {
        q.interrupt().catch(() => {});
        return message.event.message.usage;            // cache_read_input_tokens 就是读到的
      }
      if (message.type === "result") throw new Error("ended before the first frame");
    }
  } finally {
    clearTimeout(timer);
    input.end();
    q.close();
  }
}
```

**工具清单也要和真聊时一样**（进程内那个 MCP 照挂，只是调了一律回失败），工具不一样前缀就不一样。

「该不该保温」两个渠道共用一处判断。间隔可以按渠道、按模型各配一个数，用户把对话从订阅切到 API，下一次保温自己按新渠道的间隔算。

## 3.8 额度

订阅没有账单，只有「5 小时」和「本周」两个额度窗口。

- **读数来源**：流里的 `rate_limit_event`。它**只在额度变了时才来**（一个进程第一句一定来）。里面有两个窗口各自的使用率（0–1，精度 1%）和重置时刻（Unix 秒）。后端存最新一份，过了重置时刻的窗口不再显示旧数。
- **久没聊、读数旧了**：让桥起一个新进程，用最便宜的模型说一句很短的话（`maxTurns: 1`、`tools: []`、不存会话），新进程第一句一定带额度事件。失败了指数退避。
- **进了超额按量付费**（额度事件里 `isUsingOverage`）：当场停下，报错「订阅进了超额，已拦下」，不让它接着跑。账号没开超额也要拦一下，免得哪天开了不知道。

## 3.9 订阅下拿不到的东西

- **上下文窗口有多长**：订阅渠道的模型列表不带这个数。后端凡是按窗口算的地方（比如「附件太大装不下」「这一页该换了」），对不知道窗口的模型要有个默认值，别按最小的算——不然一个大文件就被莫名其妙挡住。
- **温度**：见 1.4。
- **按 token 计的花费**：只能显示额度百分比。「保温一小时大概花多少」这类提示，订阅下改成「大概用掉百分之几」，数字靠自己实测。
