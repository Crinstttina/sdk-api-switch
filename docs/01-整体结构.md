# 1. 整体结构

## 1.1 一张图

```
浏览器 / 手机
   │
   ▼
后端（组请求、存库、执行工具、记忆库、换窗……全在这里）
   │
   ├── API 渠道 ──HTTPS──▶ Messages API（或兼容的转发商）
   │
   └── 订阅渠道 ──HTTPS + 桥的钥匙──▶ 桥服务（Node，跑 Agent SDK）
                                        │  query()：一个对话一个 CLI 进程
                                        │  进程里挂一个叫 relay 的 MCP（后端的工具原样登记）
                                        ▼
                                      CLI 子进程 ──▶ Anthropic（订阅额度）
```

桥可以和后端在同一台机器，也可以在另一台。放另一台的好处是：订阅令牌只存在桥的环境里，后端碰不到；桥崩了、被攻破了，后端的数据不受影响。

## 1.2 五条原则

**一、一切以后端的数据库为准。**
后端的库里存着每条消息的原始内容块（思考块连签名、文字、工具调用和结果），这是唯一的数据源。桥上 CLI 的会话只是「为了缓存才留着的副本」：随时可以扔掉，再从后端的库里铸一份新的。桥重启、会话记录被清、换了机器，最多是这一句多写一次缓存，不会丢任何东西。

**二、组请求只有一份。**
不管走哪个渠道，后端都用同一个函数组出同一份 `system + messages + tools`，一个字节都不另拼。走 API 就直接发；走订阅就把这份东西交给桥。这样所有「塞进消息里的那几行」（时间、位置、召回的记忆、引用……）、图和文件、思考块回放，两边自动一致，不用到处写分支。

**三、连接只往一个方向。**
所有连接都由后端发起（后端 → 桥）。模型要调工具时，桥不反过来连后端，而是把这次调用当成流里的一个事件推给后端，后端执行完再发一个请求把结果交回去。后端不用开新的入站接口，出网照旧走自己的防护（SSRF 之类）。

**四、每项功能两边都能用。**
订阅只是多出来的一条路。尽量别做「只有订阅下才能用」的功能，免得哪天只能接 API 时一堆东西要改。反过来，接订阅也不许改坏或绕开 API 渠道的任何东西：没走订阅的对话，发给 API 的请求体一个字节都不该变（可以用一个钉住请求体指纹的测试守着）。

**五、不自动换渠道。**
订阅额度用完、登录失效、桥连不上，都只报错，给用户「重试」和「换个模型」两个按钮，让用户自己选。自动换到 API 等于偷偷花钱。

## 1.3 请求在哪一步分岔

两边真正不一样的只有「工具循环在谁手里」：

- **API 渠道**：循环在后端。后端问一次上游 → 回来的有工具调用就执行 → 带着结果再问一次 → 直到模型不再调工具。
- **订阅渠道**：循环在 CLI 里。后端把一整轮交给桥，CLI 自己来回问上游；中间要执行工具时，后端被叫去执行一下，执行完交回结果。

所以要先把「执行一个工具调用」（记下意图、防重复执行、真正执行、存进度）从 API 的循环里**原样抽成一个函数**，两条路共用：

```ts
// 两边共用：执行一个工具调用（记意图、防重复、执行、存进度）
async function executeTool(ctx: TurnContext, call: ToolCall): Promise<ToolOutcome> {
  const tool = ctx.tools.get(call.name);
  if (!tool) return { content: `Unknown tool: ${call.name}`, isError: true };
  if (tool.hasSideEffects) {
    recordIntent(ctx.db, call.id, call.name);         // 先落库：我要调它了
    if (!claimIntent(ctx.db, call.id)) {              // 这个调用 id 以前执行过（重试、进程重启）
      return previousResult(ctx.db, call.id);         // 绝不执行第二遍，原样交回上次的结果
    }
  }
  const outcome = await tool.run(call.input, { signal: ctx.signal });
  inTransaction(ctx.db, () => {
    if (tool.hasSideEffects) settleIntent(ctx.db, call.id, outcome);
    saveProgress(ctx.db, ctx.runId);                  // 半路断了，下次能从这里接上
  });
  return outcome;
}

// 一轮：只在最后一步分岔
async function runTurn(ctx: TurnContext) {
  const req = buildChatRequest(ctx.db, ctx.conversationId, ctx.channel); // 两边同一份
  if (ctx.channel.transport === "sdk") {
    return streamViaBridge(req, { onToolCall: (call) => executeTool(ctx, call) });
  }
  return streamDirectWithToolLoop(req, { onToolCall: (call) => executeTool(ctx, call) });
}
```

抽的时候，API 那条路的行为和请求字节都不能变。最好在抽之前就有一组测试钉住「API 这条路发了什么、执行了几次工具」，抽完全过才算。

## 1.4 渠道是一种「传输方式」

渠道表里加一列 `transport`：`http`（直连 API）或 `sdk`（经桥走订阅）。订阅渠道的**格式仍然是 Anthropic 原生格式**，所以凡是按原生格式走的东西（工具、图、PDF、思考块回放）自动都对。订阅渠道的 base URL 填桥的地址，钥匙填桥的钥匙，照常加密存。

订阅渠道下有些设置不起作用，界面上照旧显示、注明一下就好：

- **温度**：SDK 没有温度这个口子（开着思考时本来也只能是 1）。
- **缓存开关和 TTL**：CLI 自己挂缓存，固定用 1 小时档（见第 2 章）。
- **辅助模型**（起标题、写摘要、翻译这类后台小活）：建议只走 API。订阅额度留给聊天，后台小活也不该占着一个常驻进程。

模型列表：问桥（桥让 CLI 报一次 `supportedModels()`），再补上实测能用、但 CLI 列表里没报的名字（见第 6 章「模型」）。存模型时存完整 id（`claude-opus-5-5`），别存别名（`opus`）。
